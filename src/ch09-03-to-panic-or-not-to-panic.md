## 要不要 `panic!`

[ch09-03-to-panic-or-not-to-panic.md](https://github.com/rust-lang/book/blob/13e27c4a35705c4bd473bd90a3d3a8f87ef9ae58/src/ch09-03-to-panic-or-not-to-panic.md)

那麼，該如何決定何時應該 `panic!` 以及何時應該返回 `Result` 呢？如果程式碼 panic，就沒有恢復的可能。你可以選擇對任何錯誤場景都呼叫 `panic!`，不管是否有可能恢復，不過這樣就是你代替呼叫者決定了這是不可恢復的。選擇返回 `Result` 值的話，就將選擇權交給了呼叫者，而不是代替他們做出決定。呼叫者可能會選擇以符合他們場景的方式嘗試恢復，或者也可能乾脆就認為 `Err` 是不可恢復的，所以他們也可能會呼叫 `panic!` 並將可恢復的錯誤變成了不可恢復的錯誤。因此返回 `Result` 是定義可能會失敗的函式的一個好的預設選擇。

在一些類似示例、原型程式碼（prototype code）和測試中，panic 比返回 `Result` 更為合適，下文中會討論合適的原因，緊接著討論另外一種特殊情況，即有些場景編譯器無法認識這個分支程式碼是不可能走到的，但是人類可以判斷出來的，這種場景也可以用 panic!。另外章節最後會總結一些在庫程式碼中如何決定是否要 panic 的通用指導原則。

### 示例、程式碼原型和測試

當你編寫一個示例來展示一些概念時，在擁有健壯的錯誤處理程式碼的同時也會使得例子不那麼明確。例如，呼叫一個類似 `unwrap` 這樣可能 `panic!` 的方法可以被理解為一個你實際希望程式處理錯誤方式的佔位符，它根據其餘程式碼執行方式可能會各不相同。

類似地，在我們準備好決定如何處理錯誤之前，`unwrap`和`expect`方法在原型設計時非常方便。當我們準備好讓程式更加健壯時，它們會在程式碼中留下清晰的標記。

如果方法呼叫在測試中失敗了，我們希望這個測試都失敗，即便這個方法並不是需要測試的功能。因為 `panic!` 會將測試標記為失敗，此時呼叫 `unwrap` 或 `expect` 是恰當的。

### 當你比編譯器知道更多時

當你有某些其他邏輯來確保 `Result` 一定會是 `Ok` 值，而編譯器又無法理解這套邏輯時，呼叫 `expect` 也是合適的。你依然拿到的是一個必須處理的 `Result` 值：一般來說，你呼叫的這個操作仍然有失敗的可能，儘管在你的這個具體場景裡，邏輯上它不可能失敗。如果你透過人工檢查程式碼，能夠確保絕不會出現 `Err` 變體，那麼呼叫 `expect` 完全可以接受，同時最好在 `expect` 的提示文本里記錄下你為什麼認為這裡永遠不會出現 `Err`。下面是一個例子：

### 錯誤處理指導原則

在當有可能會導致有害狀態（bad state）的情況下建議使用 `panic!` —— 在這裡，**有害狀態**（*bad state*）是指當一些假設、保證、協議或不可變性被打破的狀態，例如無效的值、自相矛盾的值或者被傳遞了不存在的值 —— 外加如下幾種情況：

- 有害狀態是非預期的行為，與偶爾會發生的行為相對，比如使用者輸入了錯誤格式的資料。
- 在此之後程式碼的執行依賴於不處於這種有害狀態，而不是在每一步都檢查是否有問題。
- 沒有可行的手段來將有害狀態資訊編碼進所使用的型別中的情況。我們會在第十八章[“將狀態和行為編碼為型別”][encoding]部分透過一個例子來說明我們的意思。

如果別人呼叫你的程式碼並傳遞了一個沒有意義的值，盡最大可能返回一個錯誤，如此庫的使用者就可以決定在這種情況下該如何處理。然而在繼續執行程式碼是不安全或有害的情況下，最好的選擇可能是呼叫 `panic!` 並警告庫的使用者他們的程式碼中有 bug，這樣他們就會在開發時進行修復。類似的，如果你正在呼叫不受你控制的外部程式碼，並且它返回了一個你無法修復的無效狀態，那麼 `panic!` 往往是合適的。

然而當錯誤預期會出現時，返回 `Result` 仍要比呼叫 `panic!` 更為合適。這樣的例子包括解析器接收到格式錯誤的資料，或者 HTTP 請求返回了一個表明觸發了限流的狀態。在這些例子中，應該透過返回 `Result` 來表明失敗預期是可能的，而呼叫者就必須決定該如何處理這個問題。

當你的程式碼在進行一個使用無效值進行呼叫時可能將使用者置於風險中的操作時，程式碼應該首先驗證值是有效的，並在其無效時 `panic!`。這主要是出於安全的原因：嘗試操作無效資料會暴露程式碼漏洞，這就是標準庫在嘗試越界訪問陣列時會 `panic!` 的主要原因：嘗試訪問不屬於當前資料結構的記憶體是一個常見的安全隱患。函式通常都遵循**契約**（*contracts*）：它們的行為只有在輸入滿足特定條件時才能得到保證。當違反契約時 panic 是有道理的，因為這通常代表呼叫方的 bug，而且這也不是那種你希望所呼叫的程式碼必須處理的錯誤。事實上所呼叫的程式碼也沒有合理的方式來恢復，而是需要呼叫方的**開發者**修復其程式碼。函式的契約，尤其是當違反它會造成 panic 的契約，應該在函式的 API 文件中進行說明。

雖然在所有函式中都擁有許多錯誤檢查是冗長而煩人的。幸運的是，可以利用 Rust 的型別系統（以及編譯器的型別檢查）為你進行很多檢查。如果函式有一個特定型別的引數，可以在知曉編譯器已經確保其擁有一個有效值的前提下進行你的程式碼邏輯。例如，如果你使用了一個並不是 `Option` 的型別，則程式期望它是**有值**的並且不是**空值**。你的程式碼無需處理 `Some` 和 `None` 這兩種情況，它只會有一種情況就是絕對會有一個值。嘗試向函式傳遞空值的程式碼甚至根本不能編譯，所以你的函式在執行時沒有必要判空。另外一個例子是使用像 `u32` 這樣的無符號整型，也會確保它永遠不為負。

### 為驗證建立自定義型別

讓我們使用 Rust 型別系統的思想來進一步確保值的有效性，並嘗試建立一個自定義型別以進行驗證。回憶一下第二章的猜猜看遊戲，我們的程式碼要求使用者猜測一個 1 到 100 之間的數字，在將其與秘密數字做比較之前我們從未驗證使用者的猜測是位於這兩個數字之間的，我們只驗證它是否為正。在這種情況下，其影響並不是很嚴重：“Too high” 或 “Too low” 的輸出仍然是正確的。但是這是一個很好的引導使用者得出有效猜測的輔助，例如當用戶猜測一個超出範圍的數字或者輸入字母時採取不同的行為。

然而，這並不是一個理想的解決方案：如果讓程式僅僅處理 1 到 100 之間的值是一個絕對需要滿足的要求，而且程式中的很多函式都有這樣的要求，在每個函式中都有這樣的檢查將是非常冗餘的（並可能潛在地影響效能）。

相反我們可以在一個專用的模組中建立一個新型別來將驗證放入建立其例項的函式中，而不是到處重複這些檢查。這樣就可以安全地在函式簽名中使用新型別並相信它們接收到的值。示例 9-13 中展示了一個定義 `Guess` 型別的方法，只有在 `new` 函式接收到 1 到 100 之間的值時才會建立 `Guess` 的例項：

注意，這段位於 *src/guessing_game.rs* 的程式碼依賴於在 *src/lib.rs* 中新增 `mod guessing_game;` 模組宣告，不過這裡沒有把那部分展示出來。在這個新模組檔案裡，我們定義了一個名為 `Guess` 的結構體，它有一個名為 `value` 的欄位，用來儲存 `i32` 型別的數字。

接著，我們在 `Guess` 上實現了一個名為 `new` 的關聯函式，用來建立 `Guess` 的例項。`new` 接收一個名為 `value`、型別為 `i32` 的引數，並返回一個 `Guess`。`new` 函式體中的程式碼會檢查 `value` 是否位於 1 到 100 之間。如果 `value` 沒有透過這個測試，我們就呼叫 `panic!`，提醒呼叫這段程式碼的程式設計師：他們的程式碼裡有一個需要修復的 bug，因為建立一個 `value` 超出這個範圍的 `Guess`，會違反 `Guess::new` 所依賴的契約。`Guess::new` 在什麼條件下可能 panic，應該寫進它面向外部的 API 文件中；第十四章會講到如何在 API 文件裡表明 `panic!` 的可能性。如果 `value` 通過了測試，我們就建立一個新的 `Guess`，把它的 `value` 欄位設定為引數 `value` 的值，然後返回這個 `Guess`。

接著，我們實現了一個名為 `value` 的方法：它借用 `self`，沒有其他引數，並返回一個 `i32`。這種方法有時被稱為 *getter*，因為它的目的就是從欄位中取出一些資料並返回它。這個公有方法是必要的，因為 `Guess` 結構體的 `value` 欄位是私有的。讓 `value` 保持私有非常重要，因為這樣使用 `Guess` 結構體的程式碼就不能直接設定 `value`：`guessing_game` 模組之外的程式碼**必須**透過 `Guess::new` 來建立 `Guess` 例項，從而保證 `Guess` 不可能擁有一個未經 `Guess::new` 條件檢查的 `value`。

於是，一個接收或返回 1 到 100 之間數字的函式就可以宣告為接收（或返回） `Guess` 的例項，而不是 `i32`，同時其函式體中也無需進行任何額外的檢查。

## 總結

Rust 的錯誤處理功能被設計為幫助你編寫更加健壯的程式碼。`panic!` 宏代表一個程式無法處理的狀態，並停止執行而不是使用無效或不正確的值繼續處理。Rust 型別系統的 `Result` 列舉代表操作可能會在一種可以恢復的情況下失敗。可以使用 `Result` 來告訴程式碼呼叫者他需要處理潛在的成功或失敗。在適當的場景使用 `panic!` 和 `Result` 將會使你的程式碼在面對不可避免的錯誤時顯得更加可靠。
