## 結合起來看：Future、任務與執行緒

[ch17-06-futures-tasks-threads.md](https://github.com/rust-lang/book/blob/0d5a0dd395aba1f82d7e5aaf6dbb59b2b843ad2c/src/ch17-06-futures-tasks-threads.md)

正如我們在[第十六章][ch16]中看到的那樣，執行緒提供了一種實現併發的方式。而在本章裡，我們又看到了另一種方式：使用基於 future 和 stream 的 async。如果你想知道應該在什麼時候選哪一種，答案是：這取決於具體情況！而且在很多情況下，真正的選擇並不是執行緒*或* async，而是執行緒*和* async 一起用。

許多作業系統幾十年來一直都提供基於執行緒的併發模型，因此許多程式語言也都支援它們。但這些模型並非沒有代價。在許多作業系統中，每個執行緒都要佔用相當可觀的記憶體。執行緒也只有在你的作業系統和硬體支援它們時才可用。與主流桌面和移動裝置不同，一些嵌入式系統甚至根本沒有作業系統，因此也就根本沒有執行緒。

async 模型提供了一組不同的，而且歸根結底是互補的權衡。在 async 模型中，併發操作不需要各自獨佔一個執行緒。相反，它們可以執行在任務上，就像我們在 stream 那一節裡使用 `trpl::spawn_task` 從同步函式中啟動工作時那樣。任務和執行緒有點像，但它不是由作業系統管理，而是由庫層面的程式碼，也就是執行時來管理。

執行緒 API 和任務 API 長得這麼像並不是偶然。執行緒是“一組同步操作”的邊界；併發發生線上程*之間*。任務則是“一組非同步操作”的邊界；併發既可能發生在任務*之間*，也可能發生在任務*內部*，因為任務的函式體裡可以在多個 future 之間切換。最後，future 是 Rust 中最細粒度的併發單位，而每個 future 又可能代表一棵由其他 future 組成的樹。執行時，準確地說是它的 executor，管理任務；任務再去管理 future。從這個角度說，任務有點像“輕量級的、由執行時管理的執行緒”，只不過由於它們是由執行時而不是作業系統管理，所以又擁有了一些額外能力。

這並不意味著 async 任務就一定總比執行緒更好，反過來也一樣。線上程基礎上的併發，在某些方面其實是比 `async` 併發更簡單的程式設計模型。這一點既可能是優點，也可能是缺點。執行緒有點像 “射後不理”（“fire and forget”）：它們沒有原生對應 future 的機制，因此通常只是一路執行到結束，除非被作業系統本身打斷。

而執行緒和任務常常又能很好地協同工作，因為任務（至少在某些執行時裡）可以線上程之間來回移動。事實上，我們這一章一直使用的執行時，在底層預設就是多執行緒的，包括 `spawn_blocking` 和 `spawn_task` 在內。許多執行時會採用一種叫作 *work stealing*（工作竊取）的方法，根據各個執行緒當前的利用情況，把任務透明地線上程之間遷移，以提高系統整體效能。而這種方法本身就同時需要執行緒、任務，也就同時需要 future。

在思考什麼時候該用哪種方式時，可以先記住這些經驗法則：

- 如果工作是*非常適合並行化*的，也就是典型的 CPU 密集型任務，比如有一大批資料而且每一部分都能單獨處理，那麼執行緒通常是更好的選擇。
- 如果工作是*高度併發*的，也就是典型的 I/O 密集型任務，比如要同時處理來自很多不同來源、且到達間隔和頻率都各不相同的訊息，那麼 async 通常是更好的選擇。

如果你同時既需要並行，又需要併發，那也完全不必在“執行緒”和“async”之間二選一。你可以自由地把它們組合起來，讓每一種都去做自己最擅長的那一部分。比如，示例 17-25 展示的就是一種在現實 Rust 程式碼裡相當常見的組合方式。

我們先建立一個非同步通道，然後啟動一個執行緒，用 `move` 關鍵字把通道傳送端的所有權移入執行緒中。在那個執行緒裡，我們傳送 1 到 10 這些數字，並在每次傳送之間睡眠 1 秒。最後，我們像本章前面一直做的那樣，把一個由 async 程式碼塊構造出來的 future 交給 `trpl::block_on` 去執行。在這個 future 裡，我們等待那些訊息，就像前面那些訊息傳遞示例裡做的一樣。

回到本章一開始舉過的場景：想像一下，你用一個專門的執行緒來執行一組影片編碼任務，因為影片編碼是計算密集型工作；但當這些操作完成時，再通過一個非同步通道通知 UI。現實世界裡這類組合的例子多得數不過來。

## 總結

這不會是你在本書裡最後一次見到併發。[第二十一章][ch21]中的專案，會把這些概念放到一個比這裡那些小例子更真實的場景裡來運用，並且更直接地比較“執行緒”和“任務 / future”這兩種解決問題的方式。

無論你最終選擇哪一種方法，Rust 都為你提供了編寫安全、快速併發程式碼所需的工具，不管你的目標是高吞吐的 Web 伺服器，還是嵌入式作業系統。
