# 非同步程式設計基礎：Async、Await、Future 與 Stream

[ch17-00-async-await.md](https://github.com/rust-lang/book/blob/0d5a0dd395aba1f82d7e5aaf6dbb59b2b843ad2c/src/ch17-00-async-await.md)

很多我們要求計算機執行的操作都需要一段時間才能完成。如果在等待這些長時間執行的過程結束時，我們還能做點別的事情，就再好不過了。現代計算機提供了兩種同時處理多個操作的技術：並行和併發。然而，我們的程式邏輯通常是以近乎線性的方式編寫的。我們希望能夠描述程式應執行的操作，以及函式在哪些點可以暫停並讓程式的其他部分轉而執行，而不需要預先精確指定每段程式碼究竟該以什麼順序、用什麼方式執行。*非同步程式設計* 正是一種抽象，它讓我們能夠用“可能暫停的點”和“最終結果”來表達程式碼，而協調執行的細節則由它來替我們處理。

本章以前一章透過執行緒實現並行和併發為基礎，引入另一種編寫程式碼的方式：Rust 的 futures、streams，以及 `async` 和 `await` 語法。它們讓我們能夠表達“操作可以是非同步的”這一點；此外，還有由第三方 crate 提供的非同步執行時，用來管理和協調這些非同步操作的執行。

來看一個例子。假設你正在匯出一個家庭聚會的影片，這個操作可能要花上幾分鐘甚至幾小時。影片匯出會盡可能多地佔用 CPU 和 GPU 資源。如果你只有一個 CPU 核，而作業系統又不會在匯出完成前暫停這個任務，也就是說它會以*同步*方式執行匯出，那麼在這個任務執行期間你就什麼別的都做不了。這會是相當糟糕的體驗。幸運的是，你的作業系統可以，而且確實會，足夠頻繁地打斷匯出任務，讓你同時完成其他工作。

再假設你正在下載別人分享給你的影片。這個操作也可能耗時很長，但不會佔用太多 CPU 時間。此時 CPU 主要是在等待網路資料到達。雖然資料一開始到達時你就可以開始讀取，但全部資料到齊仍然可能需要一段時間。即便資料已經全部到達，如果影片檔案很大，完整載入它也至少可能需要一兩秒。聽起來不算長，但對於每秒能執行數十億次操作的現代處理器來說，這已經是很長的時間了。和前面的例子一樣，作業系統也會在等待網路呼叫完成時悄悄打斷程式，讓 CPU 去處理其他工作。

影片匯出屬於 **CPU 密集型**（*CPU-bound*）或 **計算密集型**（*compute-bound*）操作：它受限於 CPU 或 GPU 處理資料的速度，以及操作能分配到多少計算能力。影片下載則屬於 *I/O-bound* 操作，因為它受限於計算機的 *輸入輸出*（*input and output*）速度；它的速度最多隻能和網路傳輸資料的速度一樣快。

在上述兩個例子中，作業系統的隱式中斷提供了一種形式的併發。不過這種併發僅限於整個程式的級別：作業系統中斷一個程式並讓其它程式得以執行。在很多場景中，由於我們能比作業系統在更細粒度上理解我們的程式，因此我們可以觀察到很多作業系統無法察覺的併發機會。

例如，如果我們正在構建一個管理檔案下載的工具，程式就應該能做到：啟動一個下載任務不會讓 UI 卡死，而且使用者還能夠同時啟動多個下載任務。不過，許多作業系統中與網路互動的 API 都是 *blocking* 的；也就是說，在它們所處理的資料完全就緒之前，會阻止程式繼續向前執行。

> 注意：如果仔細想想，這其實也是*大多數*函式呼叫的工作方式。不過，*blocking* 這個術語通常保留給那些與檔案、網路或計算機上其他資源互動的函式呼叫，因為正是在這些場景中，單個程式才會從 *non-blocking* 操作中明顯受益。

我們可以為每個檔案單獨建立一個執行緒來避免阻塞主執行緒。然而，這些執行緒所消耗的系統資源最終會成為問題。更理想的情況是：這些呼叫從一開始就不是阻塞的，並且我們只需定義程式想完成的一組任務，然後讓執行時自行選擇最佳的執行順序和方式。

這正是 Rust 的 *async*（*asynchronous* 的縮寫）抽象所提供的能力。本章會介紹以下內容：

- 如何使用 Rust 的 `async` 和 `await` 語法，並藉助執行時執行非同步函式
- 如何用非同步模型解決一些我們在第十六章中已經遇到過的挑戰
- 多執行緒和非同步如何提供互補的解決方案，以及它們在許多場景下如何組合使用

不過在看到 async 的實際工作方式之前，我們需要先稍微繞個遠路，討論一下並行（parallelism）和併發（concurrency）的區別。

## 並行與併發

在上一章中，我們大致將並行和併發視為可以互換的概念。但現在我們需要更加精確地區分它們，因為它們的區別將在實際工作中顯現出來。

思考一下不同的團隊分割方法來開發一個軟體專案。我們可以分配給一個個人多個任務，也可以每個團隊成員各自負責一個任務，或者可以採用這兩種方法的組合。

當一個人在任何一個任務都還沒完成之前，就在多個不同任務之間切換工作，這就是 *併發*。一種實現併發的方式，很像你在電腦上同時 checkout 了兩個不同專案；當你對其中一個專案感到厭倦，或是在上面卡住時，就切到另一個。你只有一個人，所以不可能在完全相同的時刻同時推進兩個任務，但你可以透過在它們之間切換來多工處理，一次推進一個任務。

當團隊把一組任務拆開，讓每個成員各自負責一個任務並單獨推進時，這就是 *並行*。團隊中的每個人都可以在完全相同的時間取得進展。

在這兩種工作流中，你都可能需要在不同任務之間做協調。也許你原以為分配給某個人的任務和其他人的工作完全獨立，但實際上它必須等另一個人先完成自己的任務。有些工作可以並行完成，但其中一些實際上是 *序列* 的：它們只能按順序發生，一個接一個，如圖 17-3 所示。

<figcaption>圖 17-3：一個部分並行的工作流，其中任務 A 和任務 B 的工作相互獨立，直到任務 A3 阻塞在等待任務 B3 的結果</figcaption>

</figure>

同樣，你也可能意識到自己的一個任務依賴於另一個任務。那麼你原本的併發工作也變成了序列。

並行和併發之間也可能彼此交叉。如果你得知某位同事正在卡著，必須等你先完成某個任務，那你很可能會把全部精力都集中到那個任務上，好“解除阻塞”。這時你和同事就不能再並行工作了，而你自己也不能再併發地推進其他任務。

同樣的基礎動態也作用於軟體與硬體。在一個單核的機器上，CPU 一次只能執行一個操作，不過它仍然可以併發工作。藉助像執行緒、程序和非同步（async）等工具，計算機可以暫停一個活動，並在最終切換回第一個活動之前切換到其它活動。在一個有多個 CPU 核心的機器上，它也可以並行工作。一個核心可以做一件工作的同時另一個核心可以做一些完全不相關的工作，而且這些工作實際上是同時發生的。

在 Rust 中執行 async 程式碼時，通常是在併發地執行。至於這種併發在底層是否也會利用並行，則取決於硬體、作業系統，以及所使用的非同步執行時（稍後我們會進一步介紹非同步執行時）。

現在，讓我們深入看看 Rust 中的非同步程式設計究竟是如何工作的。
