## 共享狀態併發

[ch16-03-shared-state.md](https://github.com/rust-lang/book/blob/9bd32402af8d3103302650895ec9d129ebfa47e1/src/ch16-03-shared-state.md)

訊息傳遞是一個很好的處理併發的方式，但並不是唯一一個。另一種方式是讓多個執行緒訪問相同的共享資料。再考慮一下 Go 語言文件中的這句口號：“不要通過共享記憶體來通訊”。（“do not communicate by sharing memory.”）

通過共享記憶體進行通訊，會是什麼樣的程式碼？此外，為什麼喜歡訊息傳遞的人會警告說謹慎使用記憶體共享？

在某種程度上，任何程式語言中的通道都類似於單所有權，因為一旦將一個值傳送到通道中，將無法再使用這個值。共享記憶體類似於多所有權：多個執行緒可以同時訪問相同的記憶體位置。在 15 章中，我們介紹了智慧指標可以實現多所有權，然而這會增加額外的複雜性，因為需要管理多個所有者。Rust 的型別系統和所有權規則在正確管理這些問題上提供了極大的幫助：舉個例子，讓我們來看看互斥器（mutexes），較為常見的共享記憶體併發原語之一。

### 使用互斥器控制訪問

**互斥器**（_mutex_）是互相排斥（_mutual exclusion_）的縮寫，因為在同一時刻，它只允許一個執行緒訪問資料。為了訪問互斥器中的資料，執行緒首先需要通過獲取互斥器的**鎖**（_lock_）來表明其希望訪問資料。鎖是一個數據結構，作為互斥器的一部分，它記錄誰有資料的專屬訪問權。因此我們講，互斥器通過鎖系統**保護**（_guarding_）其資料。

互斥器以難以使用著稱（譯註：原文指互斥器在其他程式語言中難以使用），因為你必須記住兩個規則：

1. 在使用資料之前，必須獲取鎖。
2. 使用完被互斥器所保護的資料之後，必須解鎖資料，這樣其他執行緒才能夠獲取鎖。

作為一個現實中互斥器的例子，想像一下在某個會議的一次小組座談會中，只有一個麥克風。如果一位成員要發言，他必須請求或表示希望使用麥克風。得到了麥克風後，他可以暢所欲言，講完後再將麥克風交給下一位希望講話的成員。如果一位成員結束髮言後忘記將麥克風交還，其他人將無法發言。如果對共享麥克風的管理出現了問題，座談會將無法正常進行！

正確的管理互斥器異常複雜，這也是許多人之所以熱衷於通道的原因。然而，在 Rust 中，得益於型別系統和所有權，你不可能在鎖和解鎖上出錯。

<span class="caption">示例 16-12: 出於簡單的考慮，在一個單執行緒上下文中探索 `Mutex<T>` 的 API</span>

像很多型別一樣，我們使用關聯函式 `new` 來建立一個 `Mutex<T>`。使用 `lock` 方法來獲取鎖，從而可以訪問互斥器中的資料。這個呼叫會阻塞當前執行緒，直到我們擁有鎖為止。

如果另一個執行緒擁有鎖，並且那個執行緒 panic 了，則 `lock` 呼叫會失敗。在這種情況下，沒人能夠再獲取鎖，所以我們呼叫 `unwrap`，使當前執行緒 panic。

一旦獲取了鎖，就可以將返回值（命名為 `num`）視為一個其內部資料的可變引用了。型別系統確保了我們在使用 `m` 中的值之前獲取鎖。`m` 的型別是 `Mutex<i32>` 而不是 `i32`，所以**必須**呼叫 `lock` 才能使用這個 `i32` 值。我們不能忘記這麼做，因為如果沒有獲取鎖，型別系統就不允許訪問內部的 `i32` 值。

正如你所猜想的，`Mutex<T>` 是一個智慧指標。更準確的說，`lock` 呼叫會**返回**一個叫做 `MutexGuard` 的智慧指標。`MutexGuard` 智慧指標實現了 `Deref` 來指向其內部資料；它也實現了 `Drop`，當 `MutexGuard` 離開作用域時，自動釋放鎖（發生在示例 16-12 內部作用域的結尾）。這樣一來，就不會有忘記釋放鎖從而導致互斥器阻塞無法被其他執行緒使用的潛在風險，因為鎖的釋放是自動發生的。

釋放鎖之後，我們可以打印出互斥器內部的 `i32` 值，並發現我們剛剛已經將其值改為 6。

不幸的是，`Rc<T>` 並不能安全的線上程間共享。當 `Rc<T>` 管理引用計數時，它必須在每一個 `clone` 呼叫時增加計數，並在每一個克隆體被丟棄時減少計數。`Rc<T>` 並沒有使用任何併發原語，無法確保改變計數的操作不會被其他執行緒打斷。這可能使計數出錯，並導致詭異的 bug，比如可能會造成記憶體洩漏，或在使用結束之前就丟棄一個值。我們所需要的是一個與 `Rc<T>` 完全一致，又以執行緒安全的方式改變引用計數的型別。

#### 原子引用計數 `Arc<T>`

所幸 `Arc<T>` 正是這麼一個類似 `Rc<T>` 並可以安全地用於併發環境的型別。字母 _a_ 代表 **原子性**（_atomic_），所以這是一個**原子引用計數**（_atomically reference counted_）型別。**原子型別** (Atomics) 是另一類這裡還未涉及到的併發原語：請檢視標準庫中 [`std::sync::atomic`][atomic] 的文件來獲取更多細節。目前我們只需要知道：原子型別就像基本型別一樣，可以安全地線上程間共享。

你可能會好奇，為什麼不是所有的基本型別都是原子性的？為什麼標準庫中的型別沒有全部預設使用 `Arc<T>` 實現？原因在於，執行緒安全會造成效能損失，我們希望只在必要時才為此買單。如果只是在單執行緒中對值進行操作，不必強制原子性所提供的保證可以使程式碼執行得更快。

### 比較 `RefCell<T>`/`Rc<T>` 和 `Mutex<T>`/`Arc<T>`

你可能注意到了，儘管 `counter` 是不可變的，我們仍然可以獲取其內部值的可變引用；這意味著 `Mutex<T>` 提供了內部可變性，就像 `Cell` 系列型別那樣。使用 `RefCell<T>` 可以改變 `Rc<T>` 中內容（在 15 章中講到過），同樣地，使用 `Mutex<T>` 我們也可以改變 `Arc<T>` 中的內容。

另一個值得注意的細節是，Rust 不能完全避免使用 `Mutex<T>` 所帶來的邏輯錯誤。回憶一下，第 15 章中講過，使用 `Rc<T>` 就有造成引用迴圈的風險：兩個 `Rc<T>` 值相互引用，造成記憶體洩漏。同理，`Mutex<T>` 也有造成**死鎖**（_deadlock_）的風險：當某個操作需要鎖住兩個資源，而兩個執行緒分別持有兩個資源的其中一個鎖時，它們會永遠相互等待。如果你對這個話題感興趣，嘗試編寫一個帶有死鎖的 Rust 程式，接著研究其它語言中使用互斥器的死鎖規避策略，並嘗試在 Rust 中實現它們。標準庫中 `Mutex<T>` 和 `MutexGuard` 的 API 文件會提供有用的資訊。
