# 編寫自動化測試

[ch11-00-testing.md](https://github.com/rust-lang/book/blob/99071589c5358114de6324d9aa2643caeee305bd/src/ch11-00-testing.md)

Edsger W. Dijkstra 在其 1972 年的文章《謙卑的程式設計師》（“The Humble Programmer”）中說：“軟體測試是證明 bug 存在的有效方法，而要證明 bug 不存在，它就顯得遠遠不夠。”（“Program testing can be a very effective way to show the presence of bugs, but it is hopelessly inadequate for showing their absence.”）這並不意味著我們不應儘可能地做測試！

程式的正確性，指的是程式碼在多大程度上實現了我們的預期。Rust 在設計上高度重視程式的正確性，不過正確性是一個複雜且不易證明的主題。Rust 的型別系統承擔了這方面很大一部分工作，但型別系統不可能捕獲所有問題。為此，Rust 提供了編寫自動化軟體測試的支援。

假設我們編寫了一個叫做 `add_two` 的函式，它會把傳給它的數字加上 2。這個函式的簽名接受一個整數引數，並返回一個整數結果。當我們實現並編譯這個函式時，Rust 會進行目前你已經見過的所有型別檢查和借用檢查，以確保例如我們不會向這個函式傳遞一個 `String` 值或無效引用。但 Rust **無法**檢查這個函式是否真的精確實現了我們的意圖，也就是返回“引數加 2”，而不是比如“引數加 10”或“引數減 50”！這正是測試發揮作用的地方。

我們可以編寫測試斷言，比如說，當傳遞 `3` 給 `add_two` 函式時，返回值是 `5`。無論何時對程式碼進行修改，都可以執行測試來確保任何現存的正確行為沒有被改變。

測試是一項複雜的技能：雖然不能在一個章節的篇幅中介紹如何編寫好的測試的每個細節，但我們還是會討論 Rust 測試功能的機制。我們會講到編寫測試時會用到的註解和宏，執行測試的預設行為和選項，以及如何將測試組織成單元測試和整合測試。
