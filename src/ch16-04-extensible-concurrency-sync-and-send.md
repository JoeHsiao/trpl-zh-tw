## 使用 `Send` 和 `Sync` trait 的可擴充套件併發

[ch16-04-extensible-concurrency-sync-and-send.md](https://github.com/rust-lang/book/blob/9bd32402af8d3103302650895ec9d129ebfa47e1/src/ch16-04-extensible-concurrency-sync-and-send.md)

Rust 的併發模型中一個有趣的方面是：我們之前討論的幾乎所有內容，都屬於標準庫，而不是語言本身的內容。處理併發的方案並不受標準庫或語言所限：我們可以編寫自己的或使用他人編寫的併發特性。

然而，有一些關鍵的併發概念是內嵌於語言本身而非標準庫的，其中就包括 `std::marker` 的 `Send` 和 `Sync` trait。

### 線上程間轉移所有權

`Send` 標記 trait 表明實現了 `Send` 的型別值的所有權可以線上程間傳送。幾乎所有的 Rust 型別都是`Send` 的，不過有一些例外，包括 `Rc<T>`：這是不能實現 `Send` 的，因為如果克隆了 `Rc<T>` 的值並嘗試將克隆的所有權轉移到另一個執行緒，這兩個執行緒都可能同時更新引用計數。為此，`Rc<T>` 被實現為用於單執行緒場景，這時不需要為擁有執行緒安全的引用計數而付出效能代價。

因此，Rust 型別系統和 trait 約束確保永遠也不會意外的將不安全的 `Rc<T>` 線上程間傳送。當嘗試在示例 16-14 中這麼做的時候，會得到錯誤 `the trait Send is not implemented for Rc<Mutex<i32>>`。而使用實現了 `Send` 的 `Arc<T>` 時，程式碼就能成功編譯。

任何完全由 `Send` 的型別組成的型別也會自動被標記為 `Send`。幾乎所有基本型別都是 `Send` 的，除了第二十章將會討論的裸指標（raw pointer）。

### 多執行緒訪問

`Sync` 標記 trait 表明一個實現了 `Sync` 的型別可以安全的在多個執行緒中擁有其值的引用。換一種方式來說，對於任意型別 `T`，如果 `&T`（`T` 的不可變引用）實現了 `Send` 的話 `T` 就實現了 `Sync`，這意味著其引用就可以安全的傳送到另一個執行緒。類似於 `Send` 的情況，基本型別都實現了 `Sync`，完全由實現了 `Sync` 的型別組成的型別也實現了 `Sync`。

智慧指標 `Rc<T>` 也沒有實現 `Sync`，原因和它沒有實現 `Send` 時一樣。`RefCell<T>`（第十五章討論過）和相關的 `Cell<T>` 系列型別也沒有實現 `Sync`。`RefCell<T>` 在執行時進行的借用檢查不是執行緒安全的。`Mutex<T>` 實現了 `Sync`，正如[“給 `Mutex<T>` 共享訪問”][shared-access]中講到的，它可以用來在多執行緒間共享訪問。

### 手動實現 `Send` 和 `Sync` 是不安全的

通常並不需要手動實現 `Send` 和 `Sync` trait，因為完全由實現了 `Send` 和 `Sync` 的型別組成的型別，也會自動實現 `Send` 和 `Sync`。因為它們是標記 trait，甚至都不需要實現任何方法。它們只是用來強制執行與併發有關的不變性。

手動實現這些 trait 需要編寫 unsafe Rust 程式碼。第二十章會講到如何使用 unsafe Rust；目前更重要的是，要知道如果構建新的併發型別，而它又不是完全由實現了 `Send` 和 `Sync` 的部分組成，就需要認真思考，以維持其安全保證。[“The Rustonomicon”][nomicon] 中有更多關於這些保證以及如何維持它們的資訊。

## 總結

這不會是本書最後一個出現併發的章節：下一章我們會專注於非同步程式設計，並且第二十一章的專案會在更現實的場景中使用這些概念，而不像本章中討論的這些小例子。

正如之前提到的，因為 Rust 本身很少有處理併發的部分內容，有很多的併發方案都由 crate 實現。它們比標準庫要發展的更快；請在網上搜索當前最新的用於多執行緒場景的 crate。

Rust 提供了用於訊息傳遞的通道，和像 `Mutex<T>` 和 `Arc<T>` 這樣可以安全的用於併發上下文的智慧指標。型別系統和借用檢查器會確保這些場景中的程式碼不會出現資料競爭和無效的引用。一旦程式碼可以編譯了，我們就可以堅信這些程式碼可以正確地運行於多執行緒環境，而不會出現其他語言中經常出現的那些難以追蹤的 bug。併發程式設計不再是什麼可怕的概念：無所畏懼地併發起來吧！
